# CarLife HeadUnit Emulator 0.3.1 для macOS arm64 и Windows x64

Приложение для тестирования CarLife: окно проекции, управление касаниями и аппаратными командами, запрос размера/FPS видеопотока, воспроизведение принимаемого звука на компьютере и диагностика сессии. Интерфейс построен на Qt; H.264 декодируется PyAV/FFmpeg. macOS arm64 и Windows x64 используют общий интерфейс и логику сессии. Сборка macOS содержит arm64 Python, Qt, PyAV и libusb внутри `.app` и запускается без отдельной установки Python или Homebrew; Windows поставляется переносимой папкой с `CarLifeHeadUnitEmulator.exe` и зависимостями.

Версия 0.3.1 — первый отдельный GitHub-релиз приложения, выделенного из [Carlife_on_box](https://github.com/SadykovIV/Carlife_on_box). Прежнее имя версии 0.3.0 — CarLife HeadUnit. Готовые пакеты доступны в [Releases](https://github.com/SadykovIV/CarLife-HeadUnit-Emulator/releases/latest); краткое описание есть [на русском](../README.ru.md) и [на английском](../README.md). Интерфейс приложения пока русскоязычный.

Требования текущей локальной сборки macOS: **Apple Silicon (arm64), macOS 26 или новее**. Встроенные Homebrew Python и libusb собраны для macOS 26; скрипт определяет минимальную ОС по Mach-O заголовкам всех включённых arm64 библиотек и записывает её в Info.plist. Qt/PyAV сами требуют macOS 14+, поэтому сборка с другим совместимым Python/libusb может иметь более низкий минимум. Это локальная тестовая сборка с ad hoc подписью, без Developer ID и notarization Apple. Она не является сертифицированной реализацией коммерческой CarLife HU.

В Windows запускайте приложение из полностью распакованной папки; `.exe` нельзя переносить отдельно от библиотек. Наличие Windows-пакета само по себе не подтверждает работу USB-драйвера, звука и графического вывода на конкретном компьютере. Границы выполненных проверок приведены ниже.

## Запуск

Распакуйте `CarLife-HeadUnit-Emulator-0.3.1-macOS-arm64.zip` и откройте `CarLife HeadUnit Emulator.app` двойным щелчком в Finder. При сборке из исходников приложение находится в `dist/`. Его можно скопировать в `~/Applications` или другую папку: привязки к исходникам проекта нет.

В Windows распакуйте весь архив `CarLife-HeadUnit-Emulator-0.3.1-Windows-x64.zip` и откройте `CarLifeHeadUnitEmulator.exe`. Для демонстрации из PowerShell:

```powershell
& '.\CarLifeHeadUnitEmulator.exe' --demo
```

Запуск из исходников:

```sh
./tools/mac-headunit
./tools/mac-headunit --demo
```

Запуск готового приложения из терминала:

```sh
open "dist/CarLife HeadUnit Emulator.app"
open "dist/CarLife HeadUnit Emulator.app" --args --demo
```

`--demo` позволяет проверить интерфейс без телефона: встроенный MD генерирует H.264 и PCM по локальному CarLife-соединению и принимает команды. Выберите «Демо» в верхней панели; во вкладке «Подключение» можно включить тестовый тон 440 Гц перед подключением. Демонстрационные данные не являются проверкой совместимости реального CarLife устройства.

## Общий интерфейс

Компоновка следует Honda Connect Lab 0.2.6: подключение в верхней строке, вкладки под ней и большая область изображения. Сверху выбираются USB/TCP/демо и конкретное USB-устройство либо адрес TCP; рядом находятся кнопки подключения и отключения. Переключатель звука и громкость доступны рядом с вкладками и синхронизированы с панелью «Звук».

Справа внизу находится выбор темы: **«Тёмная»**, **«Светлая»** или **«Системная»**. Выбор сохраняется; системная тема следует настройке оформления ОС. Светлая тема меняет панели, текст и фон пустого экрана. Полученное с устройства изображение не перекрашивается, а поля вокруг видеокадра остаются тёмными.

В заголовке и значках приложения используется изображение Baidu CarLife+ из официальной карточки Baidu в App Store, без перерисовки и изменения цветов. Исходный файл, адрес источника, дата получения и контрольные суммы описаны в [ICON_SOURCE.json](../hu_lab/assets/ICON_SOURCE.json). Название и графика принадлежат Baidu; приложение остаётся независимым эмулятором и не является официальным продуктом Baidu или Honda.

- **Экран:** изображение на всю рабочую область, основные команды и статистика.
- **Подключение:** профиль протокола, параметры демо и переподключение в правой панели; изображение остаётся слева.
- **Видео:** запрашиваемые размер/FPS, масштаб, поворот и профиль касаний в правой панели.
- **Ввод:** USB-клавиатура AOA 2.0, раскладка, отправка текста и вставка из буфера компьютера.
- **Звук:** устройство вывода, громкость, mute и запись PCM в правой панели.
- **Диагностика:** согласованный режим потока, журнал, экспорт отчёта и переход к папке сессии.

Во время сессии выбор устройства, транспорта, адреса, профиля касаний и включение USB-клавиатуры блокируются. Параметры видео можно подготовить заранее и применить кнопкой «Применить и переподключить».

## Подключение

- **USB / AOA:** выберите нужное устройство в верхнем списке и нажмите «Подключить». AOA всегда включён для USB-подключения; отдельного флажка больше нет. Для готового Android Open Accessory интерфейса повторный переход не нужен. Если выбранное устройство ещё в обычном USB-режиме, приложение выполняет один адресный переход в AOA с проверкой его идентичности. Устройство переподключится; USB ADB может отключиться. Сканирование списка не переключает USB-режим. Приложение не устанавливает Android-компоненты и не меняет прошивку устройства.
- **TCP:** укажите адрес и порт уже запущенного совместимого лабораторного потока. Используется существующий CarLife codec проекта с мультиплексированием каналов; это не реализация произвольного CarLife Wi-Fi или старого протокола с шестью TCP-сокетами.

Настоящие устройства могут требовать отдельный профиль аутентификации CarLife или отличаться протоколом. Успешный запуск `.app` и демо не подтверждают такую совместимость. Отключение сессии освобождает ресурсы приложения.

Во вкладке «Подключение» доступны профили «CarLife v1» и «CarLife v2 · Honda». Профиль выбирается до подключения. Коммерческая OEM-аутентификация и Bluetooth HFP не реализованы.

Для запуска на явно выбранном физическом USB-порту доступна командная строка; подставьте ключ выбранного устройства вместо `PHYSICAL_KEY`:

```sh
./tools/mac-headunit --usb PHYSICAL_KEY --profile honda-v2 --width 1280 --height 720 --fps 30
```

AOA включается автоматически при подключении к выбранному `--usb` устройству. Старый параметр `--aoa-start` сохранён для совместимости команд и всё ещё требует `--usb`, но больше не меняет поведение. Обычный запуск окна и сканирование списка не начинают подключение. Те же аргументы доступны у Windows `.exe`.

## Экран, управление и звук

Размер и FPS относятся к **запрашиваемому видеопотоку CarLife**. Эти настройки не меняют разрешение рабочего стола компьютера. Удалённая сторона должна поддержать запрошенный режим; приложение не может заставить произвольную прошивку принять его. При смене геометрии проверьте принимаемый размер кадра и работу касаний.

Во вкладке «Видео» выберите 800×480, 1024×768, 1280×720, 1920×1080 или свой чётный размер и нажмите «Применить и переподключить». «Принять режим от устройства» включено по умолчанию: в «Диагностике» показаны запрошенный и реально согласованный режимы. На проверенном боксе запрос 1920×1080 привёл к ответу 1280×720; это устройство не подтвердило 1080p. Масштаб «Вписать целиком»/«Заполнить с обрезкой», поворот 0/90/180/270° и полноэкранный режим меняют только отображение на компьютере.

Мышь передаёт обычное касание и перетаскивание. Для мультитача доступны:

- Сведение и разведение пальцев на трекпаде: native zoom переводится в движение двух контактов.
- **Alt + перетаскивание мышью:** непрерывное движение двух контактов; горизонтальное движение меняет расстояние, вертикальное — угол между ними.
- **Ctrl + колесо:** масштабирование двумя контактами; на macOS также поддерживается **Cmd + колесо**. После остановки колеса контакты отпускаются автоматически.
- **Сенсорный экран:** два независимых пальца, если система передаёт приложению touch-события Qt.
- Кнопки **Pinch −/+** во вкладке «Видео» запускают готовые жесты.

Интерфейс передаёт не более **двух одновременных контактов**. Во вкладке «Видео» по умолчанию выбран **«Мультитач · 2 касания» (Legacy dual)**. **«Мультитач · Action3»** выбирается явно для совместимого устройства; профиль не определяется автоматически. «Один указатель» сохраняет обычный ввод мышью без двухпальцевых жестов. При первом чтении старых настроек 0.2.0 значение «Один указатель» заменяется новым стандартным Legacy dual; явно сохранённый выбор в 0.3.0 и ранее выбранный Action3 сохраняются.

Контакты показываются поверх изображения, учитывают поворот, масштаб и видимую область при обрезке. Выход за активную область, смена вкладки, потеря фокуса, пауза или отключение отменяют незавершённый жест. Реакция на мультитач зависит от поддержки выбранного профиля прошивкой и текущим приложением Android.

Под экраном находятся «Домой», «Назад», предыдущий/следующий трек, воспроизведение/остановка, пауза видео и снимок. Отдельно доступен запрос перезапуска видео. Доступность команд определяется подключённым устройством и выбранным профилем CarLife.

Принимаемые Media/TTS/VR PCM-пакеты воспроизводятся через выбранное аудиоустройство компьютера. Во вкладке «Звук» выбираются выход, громкость приложения, mute и сохранение PCM в WAV (до 8 MiB; включается со следующей сессии). Доступность звука зависит от того, передаёт ли удалённая сторона поддерживаемый аудиоформат. Микрофон не захватывается.

Декодер уведомляет интерфейс о новом кадре через очередь Qt; одновременно ожидает не более одного уведомления, а для показа берётся последний готовый кадр. Таймер 33 мс остаётся запасным механизмом. На macOS активная сессия запрашивает системный activity token против App Nap; он освобождается при отключении, ошибке подключения и выходе. Эта активность разрешает обычный сон системы. Если системный API недоступен, поток продолжает работать, а причина сохраняется в диагностике. На Windows вызовы API macOS не выполняются.

## Клавиатура и вставка текста

Во вкладке **«Ввод»** флажок **«Клавиатура по USB»** включает дополнительную HID-клавиатуру AOA 2.0 на уже выбранном и открытом USB-устройстве. Он применяется при следующем подключении и включён по умолчанию. Этот флажок управляет только клавиатурой; режим AOA основного USB-подключения всегда включён. Регистрация HID начинается после установления потока CarLife. Используется версия AOA, полученная при подключении; повторный GET_PROTOCOL не отправляется. Для уже включённого аксессуара с неизвестной версией поддержка проверяется самой регистрацией HID. Устройство должно принять регистрацию клавиатуры AOA 2.0. Готовность и ошибки показаны в этой же вкладке; недоступность клавиатуры не останавливает CarLife-поток.

Для ввода текста:

1. Подключите устройство по USB и дождитесь состояния готовой USB-клавиатуры во вкладке «Ввод».
2. Выберите **English (US)** или **Русская (ЙЦУКЕН)**. На Android должна быть выбрана **такая же раскладка физической клавиатуры**, а **Caps Lock выключен**. Приложение не переключает раскладку Android автоматически.
3. Щёлкните по текстовому полю на изображении устройства и печатайте с клавиатуры компьютера. Можно также подготовить текст во вкладке «Ввод» и нажать **«Отправить текст»**.
4. Для вставки нажмите **Ctrl/Cmd + V** при фокусе на изображении либо кнопку **«Вставить текст из буфера»**. Кнопка **«Остановить ввод»** отменяет ещё не отправленную часть очереди.

Вставка работает **только от компьютера к устройству**: текст локального буфера передаётся как последовательность нажатий USB-клавиатуры в активное поле Android. Буфер и текст Android обратно не читаются, удалённый буфер не синхронизируется. Локальный буфер читается только по явной команде вставки при готовой USB-клавиатуре. ADB для ввода не используется, дополнительные Android-компоненты не устанавливаются. Содержимое отправляемого текста не записывается в журнал и диагностический отчёт.

Это ввод через физические клавиши, поэтому поддержаны символы выбранной раскладки: печатные символы ASCII для US, стандартная ЙЦУКЕН с цифрами и знаками препинания для RU. Произвольный Unicode, эмодзи и автоматическое смешивание раскладок не поддерживаются. Весь текст проверяется до постановки в очередь: неподдерживаемый символ отклоняет отправление целиком. Одно отправление ограничено 4096 символами; очередь также ограничена. Переходы строк и табуляция передаются клавишами Enter и Tab, поэтому могут менять фокус или выполнять действие в текущем поле Android.

Для TCP и демо доступны команды CarLife с клавиатуры: стрелки, Enter, Esc, Home и мультимедийные клавиши. Ввод текста и вставка требуют USB AOA 2.0. Успешная отправка HID-отчётов подтверждает выполнение USB-запросов, но не появление текста в поле: **доставка текста на реальном устройстве для версии 0.3.1 пока не подтверждена**.

## Данные тестов

По умолчанию настройки и результаты сохраняются в `~/Library/Application Support/CarLife HeadUnit/` на macOS и `%LOCALAPPDATA%\CarLife HeadUnit\` на Windows. Прежнее имя папки намеренно сохранено в 0.3.1 для совместимости с настройками и сессиями старых версий. В `sessions/` создаётся отдельная папка каждого подключения: протокольные события, счётчики, `desktop-summary.json`, снимки и включённые аудиозаписи. Кнопки «Папка сессии» и «Экспорт отчёта» находятся во вкладке «Диагностика». Аргумент `--data-dir /path/to/data` переопределяет папку данных; записи внутрь установленного приложения не требуются.

## Сборка из исходников

Сборку macOS нужно выполнять на Apple Silicon с **arm64 Python 3.11+**, без Rosetta. Для первой сборки:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r macos/requirements-build.txt
brew install libusb
./tools/build-mac-headunit
```

Скрипт выбирает `HU_PYTHON`, затем `.venv/bin/python`, затем `python3` из PATH. Для явного выбора интерпретатора:

```sh
HU_PYTHON=/absolute/path/to/python ./tools/build-mac-headunit
```

Результат: `dist/CarLife HeadUnit Emulator.app`. Промежуточные файлы и отчёт проверки: `build/mac-headunit/`. Можно передать `--dist-dir /absolute/output/path`, `--libusb /path/to/libusb-1.0.dylib` и `--clean` для чистого анализа PyInstaller.

Сборка автоматически проверяет arm64 архитектуру исполняемого файла, целостность локальной подписи и загрузку всех основных Python/Qt/PyAV/libusb компонентов из готового bundle. Проверка не открывает устройство и не создаёт GUI.

Сборщик переносимого Windows x64 пакета находится в `windows/build.py`; фиксированные версии и SHA-256 зависимостей — в `windows/dependencies.json`. Он запускается на macOS/Linux с Python, Pillow и инструментами LLVM (`clang`, `lld-link`, `llvm-dlltool`, `llvm-rc`). На macOS после установки зависимостей Python выполните:

```sh
brew install llvm
./tools/build-windows-headunit
```

В `dist/` появятся папка и ZIP `CarLife-HeadUnit-Emulator-0.3.1-Windows-x64`. Параметры `--cache-dir`, `--dist-dir` и `--replace` управляют кешем, выходной папкой и повторной сборкой. Сборщик проверяет зависимости и PE, но не запускает Windows-код.

Общая точка входа приложения — `hu_lab.desktop`, Windows-обёртка — `windows/entry.py`. Запуск исходников на Windows после установки desktop-зависимостей:

```powershell
python -m hu_lab.desktop --demo
```

Полный набор автоматических тестов запускается из корня репозитория после установки `requirements-hu.txt`:

```sh
python -m unittest discover
```

Тесты используют локальные loopback-сокеты, синтетический MD и подменённый USB; реальные устройства не открываются. Без PySide6/PyAV часть desktop-тестов пропускается, поэтому для полной проверки нужны все desktop-зависимости.

## Проверка готовой сборки

15 октября 2026 года предыдущая macOS-сборка проверена на подключённом боксе: 1660 декодированных кадров 1280×720 за 55,27 секунды, 318 отправленных пакетов ввода и 4 189 440 байт PCM передано в CoreAudio без зарегистрированных потерь в аудиобуфере. Пользователь подтвердил, что слышит звук. Это результат конкретной сессии и устройства; он не подтверждает совместимость со всеми реализациями CarLife, поддержку 1080p данным MD, новые способы ввода 0.3.0 или аппаратную проверку Windows-сборки.

23 октября 2026 года общий интерфейс 0.2.0 проверен offscreen-тестами на macOS с синтетическим CarLife MD: выбор устройства и сохранение выбора после обновления списка, автоматический AOA на границе подключения при подменённом USB, видимость вкладок, восстановление настроек, синхронизация звука, касания и команды, пауза/перезапуск, смена разрешения с переподключением, вывод кадров без периодического таймера, очистка сессии, жизненный цикл activity token и продолжение работы при недоступности этого API. USB в этих тестах не открывается; activity backend подменён. Это проверка поведения общего кода, а не подтверждение работы реального USB, Windows GUI/аудиоустройства или влияния App Nap на реальную сессию.

### Исправление USB/HID в 0.3.1

AOA использует стандартные строки Baidu / CarLife / 1.0.0, совпадающие с USB-фильтрами HeadSwap и CarProjection. Прежние строки Mac HU Lab / CarLife HU переключали режим USB, но не запускали эти приложения. Исправлены ID клавиатуры (1 вместо 17228), повторный GET_PROTOCOL после перехода в AOA и лишние RELEASE/UNREGISTER после отказа регистрации. Ошибка отменённого чтения больше не скрывает исходный тайм-аут записи. Ограничение ID и побочные эффекты GET_PROTOCOL сверены с [драйвером Android](https://android.googlesource.com/kernel/common/+/refs/heads/android15-6.6/drivers/usb/gadget/function/android_f_accessory.c). Если предыдущая сборка уже оставила аксессуар без ответа, отключите сеанс и один раз переподключите USB перед проверкой исправления.

26 октября 2026 года после этих исправлений запуск из исходников с устройством HeadSwap достиг STREAMING, декодировал 4 кадра до регистрации HID и 7 суммарно после неё. Регистрация клавиатуры и завершение сеанса прошли без ошибок, рабочих потоков после остановки не осталось. Текст не отправлялся: это проверка подключения и регистрации, а не доставки символов в Android-поле.
